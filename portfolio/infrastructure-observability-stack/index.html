INFRASTRUCTURE OBSERVABILITY STACK

Ansible-driven metrics and centralized logging for infrastructure and Docker workloads.

Ansible Grafana Prometheus Loki Grafana Alloy Docker

Project Overview

This project builds a repeatable observability environment for Linux hosts and Docker workloads. Ansible manages installation and configuration, Grafana Alloy collects telemetry from monitored hosts, Prometheus stores metrics, and Loki centralizes eligible container logs. Grafana provides a unified interface for querying and exploring both data types.

The case study focuses on the Single Instance deployment profile and documents the engineering directions for extending the platform toward High Availability and higher-scale deployments.

Architecture

Monitoring Clients

Linux hosts and Docker workloads provide host metrics and container logs.

Grafana Alloy

Agents collect host metrics and conditionally forward Docker log files.

Observability Server

Prometheus and Loki store telemetry for exploration through Grafana.

Metrics path: Monitoring clients → Grafana Alloy → Prometheus remote-write → Grafana.
Logs path: Docker json-file log discovery → Grafana Alloy → Loki → Grafana.

Grafana uses provisioned Prometheus and Loki data sources. The services communicate over the configured monitoring network; network exposure should remain restricted to trusted systems.

Metrics Collection

Grafana Alloy runs on monitoring client hosts and collects host-level metrics. It sends those metrics to the central Prometheus remote-write endpoint, where they are retained for querying and dashboard visualization.

  • Host metrics are collected by Alloy on monitored clients.
  • Prometheus receives metrics through its remote-write receiver.
  • The documented lab defaults retain Prometheus metrics for 15 days.
  • Grafana dashboards provide host and container resource visibility.

Centralized Logging

Container log collection is conditional. A discovery helper identifies active Docker containers using the json-file logging driver and makes their log files available to Alloy. Alloy forwards configured targets to Loki for centralized querying in Grafana.

  • Only eligible containers using the json-file driver are discovered.
  • A temporary log generator is available to validate the log pipeline.
  • Grafana's log exploration dashboard supports filtering and inspection of container logs.
  • The documented lab default for Loki retention is 168 hours (7 days).

Applications must emit useful structured or consistently formatted logs for application-level analysis. Log collection does not automatically guarantee that every application event contains the fields needed for every dashboard query.

Grafana Dashboards

Container Resource Overview

Resource-focused panels provide visibility into CPU and memory utilization, top resource-consuming containers, and host disk usage. These views help identify resource pressure and compare workloads.

Container Logs Explorer

Log-focused panels support container log inspection, error and warning exploration, HTTP request-path analysis, and identification of slow HTTP requests where the application emits the expected request fields.

Dashboard definitions are maintained as version-controlled JSON files in the repository. This keeps dashboard changes reviewable and repeatable alongside the infrastructure configuration.

Infrastructure Automation with Ansible

Ansible is used to automate the monitoring server and client configuration. The guided quick-start.sh workflow validates the lab configuration and secrets, checks playbook syntax, verifies SSH connectivity, and runs preflight checks before deployment.

  • Single Instance deployment is the implemented deployment profile.
  • Inventory separates lab host definitions, local monitoring settings, and production examples.
  • Container image versions, network bind addresses, and monitoring defaults are configurable.
  • ./quick-start.sh --check performs configuration, connectivity, and read-only preflight checks without deploying.
  • SSH host-key verification is enabled by default.

The deployment workflow is designed to be repeatable, with idempotency applied through Ansible roles where supported. Environment-specific values and credentials remain outside version control.

Security and Operations

  • Keep Grafana, Prometheus, and Loki accessible only from trusted networks.
  • Store Grafana credentials and secret keys in the local secrets file; never commit them.
  • Use dedicated SSH credentials and least-privilege access where practical.
  • Protect cAdvisor and its Docker socket access; a read-only socket mount does not restrict Docker API operations.
  • Review log contents, backup access, and retention because telemetry may contain sensitive information.

Persistence and Backup Scope

Grafana, Prometheus, and Loki use persistent Docker volumes. The repository includes a profile/configuration archive workflow, but that archive is not a backup of monitoring volumes or historical metrics and logs. Monitoring-data backup and restoration still require implementation and recovery testing before they can be treated as an operational guarantee.

Testing and Validation

The repository includes validation for the deployment workflow and version-controlled Grafana dashboards. Dashboard tests have been run with pytest to check dashboard structure and query-related expectations. The guided check-only mode also validates configuration, SSH connectivity, and read-only preflight conditions without applying deployment changes.

A temporary log generator can be used to produce sample stdout events and verify that eligible Docker logs reach Loki and can be explored through Grafana.

Future Engineering Directions

The next iterations focus on strengthening recovery capabilities, availability, and operational visibility beyond the documented Single Instance deployment profile.

  • Implement and validate monitoring configuration backup and recovery.
  • Design and test backup and restoration for historical metrics and logs.
  • Build and validate a High Availability deployment profile.
  • Evaluate scale-out architecture and deployment automation.
  • Expand dashboard coverage, alerting, and operational validation.
